# Баримт ба цахим гарын үсэг · Documents & e-signatures

`io.example.documents` апп нь баримтыг батлах урсгалд оруулж, иргэний **бодит
eID батламжаар** гарын үсэг зуруулдаг. Энэ бичиг нь тэр урсгалын ойлгомжгүй
хэсгүүдийг — яагаад тийм болсныг — тайлбарлана.

---

## 1. Гарын үсэг гэж юу вэ

eID Mongolia-д **баримт зурах endpoint байхгүй**. Байгаа зүйл нь: иргэн өөрийн
бүртгэлтэй төхөөрөмж дээр, өөрийн гэрчилгээгээр, RP-ийн сонгосон текстийн эсрэг
өгдөг батламж. **Тэр батламж нь өөрөө гарын үсэг.**

Тиймээс ceremony нь хоёр дуудлагатай:

```
POST /documents/{id}/sign/eid/start   иргэний eID апп руу батлах хүсэлт түлхэнэ
POST /documents/{id}/sign/eid/poll    батлах / татгалзах / хугацаа дуусахыг хүлээнэ
```

`poll` нь COMPLETE буцаах мөчид гарын үсэг бүртгэгдэнэ. Live горимд API нь
хүсэлтийг 25 секунд хүртэл онгойлгож барьдаг тул клиент `AbortSignal` дамжуулж,
дэлгэц хаагдмагц тасалдаг.

### Харагдах текст нь хамгаалалт

Иргэнд харагдах текст баримтыг **нэрлэдэг**:

```
«Хамтран ажиллах гэрээ 2026» баримтад гарын үсэг зурах
```

«Gerege ERP-д нэвтрэх» гэдгийг батлах нь гэрээнд гарын үсэг зурахыг зөвшөөрөх
**биш**. Иргэн юуг батлаж байгаагаа зөвхөн энэ текстээр мэддэг тул баримтыг
нэрлэхгүй бол батламж нь ямар ч утгагүй болно.

eID текстийг хязгаарладаг. Урт гарчгийг **rune-аар** хайчилдаг — байтаар
хайчилбал кирилл үсэг дундуур тасарна.

### Session нь баримттай холбогдсон, нэг удаагийн

`document_eid_sign_sessions` (migration `00012`) нь session-ыг **эхлүүлсэн
баримттайгаа** хамт хадгална. Ингэснээр:

- A баримтын нэрийг харж өгсөн батламжийг B баримт дээр бичих боломжгүй;
- session нэг гарын үсэг гаргасны дараа `consumed_at` тэмдэглэгдэж, дахин
  хэрэглэгдэхгүй (дахин poll хийвэл аль хэдийн гарсан баримтыг буцаана);
- өөр tenant session id-г гартаа авсан ч poll хийж чадахгүй.

Батлахыг буцаасан регистр нь **push илгээсэн** регистртэй таарах ёстой. Bodlogo
ба батлах хэлхээг эхлэх үед биш, **дуусах үед** дахин уншина — хооронд минут
өнгөрсөн байж болох тул шийдэх нь тэр мөч.

### ДАН яагаад өөр вэ

ДАН нь энэ платформд батлах push түлхдэггүй. Тиймээс `POST
/documents/{id}/sign/dan` нь регистр + нэг удаагийн кодын хэлбэрээрээ хэвээр, бас
`DAN_MOCK_MODE` унтарсан үед ажиллахгүй — live ДАН OTP клиент кодод байхгүй.
Дэлгэц дээр суваг тус бүр өөрийн юу хийдгээ бичдэг.

## 2. Хэн зурж болох вэ

Гурван зүйл шийднэ:

| Хаана | Юу шийднэ |
|---|---|
| `documents.sign` эрх | Ерөөсөө гарын үсэг зурах/татгалзах эрхтэй эсэх |
| Гарын үсгийн бодлого (`/module/documents/signatures`) | Ямар сувгаар (E-ID/ДАН), зөвхөн нэрлэсэн хүн эсэх |
| Батлах хэлхээ (`/module/documents/workflows`) | Хэдэн хүн, ямар дараалалтай, хэн нэрлэгдсэн |

`documents.sign` нь **зориудаар** `documents.manage`-аас салангид: баримт
зохиох нь гарын үсэг зурах эрх биш. Сервер тал дээр
`appRequestPermission` нь `/sign/…` ба `/reject`-ыг `documents.sign`-аар шалгана
(`/signatures` уншилт нь `documents.read` хэвээр).

> **Анхаар:** tenant үүсэх үеийн trigger нь `admin`-д тухайн үед байгаа бүх
> эрхийг, `manager`/`user`-т зөвхөн `%.read` ба `%.manage`-ыг олгодог. Тиймээс
> `documents.sign` нь manager/user-т **хэзээ ч автоматаар** олгогдохгүй — tenant
> админ өөрөө олгох ёстой. Эрхийн мөр өмнө нь суулгасан tenant-уудад байдаггүй
> байсныг migration `00013` нөхсөн.

### Хоёр тийш нь хаагдахаас сэргийлсэн

Bodlogo «зөвхөн нэрлэсэн хүн» шаардаж байхад хэлхээ хэнийг ч нэрлээгүй бол тэр
төрөл **хэнд ч** зурагдахгүй болно. Тиймээс:

- хэлхээ хэнийг ч нэрлээгүй байхад тэр bodlogo хадгалагдахгүй;
- bodlogo шаардсаар байхад хэлхээ сүүлчийн нэрлэсэн хүнээ хаяж чадахгүй.

## 3. Хэдэн гарын үсэг

`document_signatures` (migration `00011`) нь **ledger**: гарын үсэг тутамд нэг
мөр, `(баримт, зурагч)` хосоор unique — нэг хүн хоёр батламж болж тоологдохгүй.

Шаардлагатай тоо нь тухайн төрлийн хэлхээний шатны тоо; хэлхээ байхгүй бол
**нэг** гарын үсэг батална (энэ нь хэлхээ гарахаас өмнөх зан). Хэлхээ дуусахад
л баримт `APPROVED` болно, түүнээс өмнө `PENDING_APPROVAL` хэвээр 1/3, 2/3 гэж
явна.

Дуусгавар болсныг шийддэг тоолол нь баримтын мөрийг **`FOR UPDATE`-ээр
цоожилсон** дотор уншигдана — эс бөгөөс зэрэг ирсэн хоёр зурагч хоёулаа
хоцрогдсон тоо хараад баримт 2/2 гарын үсэгтэй боловч PENDING хэвээр гацна.
Иргэний танилтын дуудлага цоожийн **гадна** байрлана: eID-ийн сүлжээний
хүсэлтийг мөр цоожилсон хэвээр хийж болохгүй.

`document_records` нь хамгийн сүүлийн гарын үсгийг өөр дээрээ тольдож хадгална,
ингэснээр жагсаалт нэг query хэвээр байна. Бүтэн түүх нь ledger-т.

---

## 4. Төлөвийн эргэлт

```
DRAFT ──POST /{id}/route──▶ PENDING_APPROVAL ──хэлхээ дуусав──▶ APPROVED
                                    │
                                    └──POST /{id}/reject──▶ REJECTED
```

`CreateDocument` нь шууд `PENDING_APPROVAL` бичдэг тул аппын үүсгэсэн зүйл
ноорог болдоггүй. `DRAFT` нь баганын үндсэн утга бөгөөд `route` нь өөр замаар
орж ирсэн мөрийг хөдөлгөнө. Дэлгэц дээр таних төлөв бүр өөрийн шошготой,
**танихгүй** төлөв raw хэвээр харагдана — «Хүлээгдэж буй» гэж худлаа хэлэхгүйн
тулд.

## 5. Аудит

Гарын үсэг зурах нь энэ модулийн хамгийн аудит шаардсан үйлдэл. `audit.Record`
дараах зүйлсийг бичнэ:

| Үйлдэл | Хэзээ |
|---|---|
| `documents.signature_requested` | eID батлах хүсэлт илгээхэд (хэн **асуусан**) |
| `documents.signed` | Гарын үсэг бүртгэгдэхэд (хэн **зурсан**, суваг, гэрчилгээ, хэлхээ дуусав уу) |
| `documents.rejected` / `documents.routed` | Татгалзал / батлахад илгээх |
| `documents.signature_policy_changed` / `.approval_chain_changed` / `.retention_rule_changed` | Тохиргоо |
| `documents.template_created` / `.template_deleted` | Загвар |

Асуусан хүн ба зурсан хүн **хоёр өөр** зүйл: ledger нь зөвхөн хоёр дахийг мэддэг
тул хүсэлтийг тусад нь бичдэг.

## 6. Тест

```bash
# Нэгж тестүүд — DB шаардахгүй
go test ./internal/apps/documents/

# Бүрэн тестүүд — migration хийсэн хаяж болох DB шаардана
DOCUMENTS_TEST_DATABASE_URL=postgres://... go test ./internal/apps/documents/
```

Integration тестүүд нь SQL дотор амьдардаг зүйлсийг барина: төлөвийн хамгаалалт,
нэг зурагч нэг л удаа гэсэн constraint, хэлхээнээс гарах тоолол, tenant-ийн
хуваалт, бас гол хоёр нь — **батламжийг өөр баримт руу зөөж болохгүй** ба
**session нь өөр tenant-д хамаарахгүй**.

CI нь `DOCUMENTS_TEST_DATABASE_URL`-ыг тавьж, тестүүд чимээгүй skip болвол job-ыг
унагадаг — gov_services-д байдгийн адил, эс бөгөөс skip нь pass шиг харагдана.

## 7. Одоогийн цоорхойнууд

- **ДАН live биш.** `AuthenticateDANCitizen` нь mock-гүйгээр алдаа буцаана.
- **Прод дээр E-ID** нь `EID_MOCK_MODE=false` үед бодит холбогчоор ажиллана
  (`EID_RP_UUID`/`EID_RP_SECRET` шаардана); mock горимд батламж 1.5 секундын
  дараа өөрөө "батлагдана".
- **Зурагчийг нэвтэрсэн хэрэглэгчтэй тулгадаггүй.** `users` хүснэгтэд регистр
  хадгалагддаггүй (eID linking нь зориудаар PII биш digest хадгалдаг). Одоогоор
  хэлхээнд нэрлэгдсэн регистртэй л тулгаж болно.
- **Загварт агуулга байхгүй** — баримт нь гарчиг + төрөл.
- **Хадгалалт юу ч устгадаггүй** — хугацаа дууссаныг л тайлагнана.
- **Эрхийн нэр/тайлбар зөвхөн англи** — `internal.PermissionDefinition`-д
  `Labels` талбар байхгүй (платформын цоорхой, `TRANSLATION_GUIDE.md` §7).
